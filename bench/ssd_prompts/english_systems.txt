A regional library is replacing its catalog service while keeping public access available. The existing service stores book records, lending events, and borrower identifiers in one database. Three branches share that database, but each branch keeps a local queue of lending events when its network connection fails. Some events arrive hours after they occurred. The migration team has a recent backup and a separate staging environment, but it cannot assume that every branch will remain online during the change.

The new catalog separates descriptive book metadata from lending state. A book can have several physical copies, each with its own identifier. A lending event refers to a physical copy rather than to the title. Corrections sometimes arrive as later events that reverse an earlier transaction. Two librarians can work with the same copy during an outage, so the migration must preserve enough information to investigate conflicts rather than silently choosing whichever event arrives last. Public search should remain available even if lending updates are temporarily delayed.

The project manager wants a migration plan with a reversible cutover. She needs to know which invariants to check before switching traffic, how to compare the old and new services, and how to handle events that arrive during the transition. A nightly count of all rows is insufficient because two incorrect records can cancel each other out in an aggregate count. The team also needs a record of the exact transformation applied to each category of data, together with a clear explanation of what would trigger rollback.

Explain a practical sequence of steps. Pay particular attention to identifiers, delayed events, conflict detection, and evidence that the new lending state agrees with the original history. Describe how you would test the process before using it at all three branches.
